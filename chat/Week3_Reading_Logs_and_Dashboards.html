01

Anatomy of a log line

Every time anything happens in RPS — a login, a scenario start, an AI call — the backend writes a line describing it. RPS uses structured JSON logging, meaning each line is a JSON object with the same handful of fields every time. Once you know the fields, you can skim hundreds of lines in seconds.

{ "timestamp": "2026-08-27T09:14:02Z", "severity": "ERROR", "session_id": "a3f9-88bd-...", "service": "gemini-live-backend", "message": "Gemini session closed unexpectedly", "context": { "reconnect_attempted": true } }
Fig 1. A realistic RPS log line, field by field.
FieldWhat it tells you
timestampExactly when — essential for lining up events across two services (see Section 2)
severityHow serious: INFO (normal), WARN (worth noting), ERROR (something failed)
session_idWhich specific simulation this belongs to — your single most useful filter
serviceWhich of RPS's two backends wrote this line — first thing to check per Week 2
messageThe plain-English summary — read this first, always
contextExtra details specific to this event — the "why," once you know the "what"
RPS connection This mirrors the closure report's own note that the Gemini Live backend uses "structured JSON logging" — and it lines up with the ai_usage_logs table in the Technical Design Document, which records session_id, tokens_generated, and duration_seconds for every AI interaction. Logs and database tables often track the same underlying event from two different angles.

02

Tracing one request across two backends

Remember from Week 2: RPS runs two independent backends. When a trainee's simulation misbehaves, its story is split across both — and the thread that ties the pieces together is the session_id.

Fig 2. One session_id, three places to look — the core move of Week 3.

The workflow, step by step:

  1. Get the session_id for the affected simulation — from a trainee's complaint, the URL, or a database row.
  2. Search the NestJS backend logs for that ID — confirm the session was created and ended correctly.
  3. Search the Python backend logs for the same ID — this is where voice/AI-specific failures show up.
  4. Check the relevant database table (sessions, evaluations) — confirm what was actually saved.
Why this matters for you Without a shared ID, you're guessing which of hundreds of log lines belongs to the incident you care about. With it, you go from "a wall of text" to "these six lines, in order." This one habit is worth more than memorizing any error code.

03

RPS's real error codes, decoded

Week 1 covered status codes in general. Here's exactly how RPS itself uses each one — pulled directly from the Technical Design Document's authentication and authorization logic.

CodeRPS's actual triggerWhat you now know
200 OKe.g. logout, password reset — even wrong email on "forgot password" returns 200 (deliberately, to prevent attackers from discovering valid emails)200 doesn't always mean "succeeded as the user hoped" — check the message body too
401 UnauthorizedJWT missing, expired, or invalid (access tokens expire every 30 minutes)Self-service — tell the user to log in again; not an engineering issue
403 ForbiddenCasbin RBAC check fails — e.g. a trainee's role doesn't include the route they hitCheck the user's role, not their login — this is a permissions issue, not an auth issue
429 Too Many RequestsOTP resend hit more than 3 requests in 5 minutes (retry_count)Expected protective behavior — tell the user to wait, don't escalate
500Anything unhandled — a bug, a downstream service failing, a bad deployThe one code that's never "expected" — this is what you escalate
RPS connection Notice how 401 and 403 look similar to a user ("I can't get in!") but mean completely different things to you. 401 says "this person isn't proven to be who they claim." 403 says "we know who they are, and they're not allowed here." Mixing these up sends you down the wrong fix every time.
Try this with Claude Take a real (sanitized) error log from a past RPS incident. Paste it in and ask: "Based on this status code and message, is this a 401, 403, 429, or 500 situation — and what does that tell me about who needs to act on it?"
04

Finding these logs in GCP Cloud Logging

All of the log lines above end up in one place: GCP's Logs Explorer. You don't need to be a GCP expert — you need three moves.

  • Filter by severity — start with ERROR to cut noise, widen to WARNING if nothing turns up.
  • Filter by resource — narrow to the GKE cluster (autopilot-cluster-1 from Week 2) and the specific service (NestJS vs. Python) so you're not wading through both at once.
  • Search by session_id — paste the exact ID into the query bar; this is the single highest-value search you'll run.
Plain-English translation A "health check" endpoint (mentioned in the closure report for both backends) is a tiny route each service exposes that just replies "I'm alive." Monitoring pings it constantly — if it stops replying, that's your fastest possible signal that a whole service is down versus just one feature being broken.
